# Contract conventions

- Use `openapi: 3.1.0` and YAML 1.2. OpenAPI 3.1 Schema Objects follow JSON Schema Draft 2020-12. `info.title` and `info.version` describe the contract, not the OAS version.
- The default location is `<project>/src/main/resources/openapi/modules/<module>.yaml`, one standalone OpenAPI entry document per application module. Each module owns paths, parameters, business schemas, and success responses. Standardized errors and `ProblemDetail` live together in `openapi/common/responses.yaml`; module error responses reference `../common/responses.yaml#/components/responses/<ResponseName>`. Inside that common fragment, references such as `#/components/schemas/ProblemDetail` resolve against the fragment itself. Shared security can live in `common/security.yaml` when specified. The older root-level module entries and `openapi.yaml` with `paths/<profile>.yaml` remain supported for projects already using them. Keep `$ref` relative to the referring file. A path template such as `{customerId}` must have a matching required path parameter.
- GET and HEAD have no request body. HEAD and 204 responses have no content. POST commonly returns 201 for creation, but use 200 for an operation that does not create a resource. PUT replacement and PATCH partial updates have distinct request schemas when their fields differ. Avoid describing a PATCH payload as a full replacement.
- Infer JSON types from supplied examples only: object, array, string, integer, number, boolean, null. Examples do not establish required properties, formats, enums, bounds, or authentication. Add those only when the developer specifies them or an existing contract clearly establishes the rule. Request and response schemas are separate even when examples look alike.
- Parameter location must be explicit except for names in a path template. In OpenAPI, `query`, `header`, `path`, and `cookie` are supported. Path parameters are always required; other parameters are required only if specified. Use `schema` for their types. Do not document duplicate names in the same location.
- Document only behavior the developer described or the existing contract establishes. Supply at least one response for each operation. Select a status consistent with the operation, and do not invent error bodies. When error structure is supplied, use a shared error schema where appropriate.
- Use stable `operationId`s unique across all module contracts, short summaries, useful descriptions, and one primary tag per module or resource. Reuse existing names and components when extending a contract. Never replace an unrelated path or component.
- The source contracts are authoritative. The bundle is an output artifact only in the legacy single-entry layout; regenerate it after every legacy change. Validate each module entry document independently for YAML syntax, OpenAPI structure, and reference resolution. Review warnings that indicate a contract defect.
